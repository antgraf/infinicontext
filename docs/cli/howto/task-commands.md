# Using `/task` commands

InfiniContext tracks units of work as **tasks**. A task is a stable, named, durable
piece of work — bigger than a single Claude session, smaller than the whole
project. Each task has a folder under your repo's `.task/` with a few markdown
artifacts (a description, a progress log, an index of files) and a row in the
host's per-machine SQLite registry under `~/.infinicontext/infinicontext.db` that
gives it a globally durable id.

`/task` commands are typed at the InfiniContext REPL prompt. They don't talk to
the spawned `claude` child — they're host-side actions managed by the
InfiniContext CLI itself.

## At a glance

| Command | What it does |
|---|---|
| `/task new "<description>"` | Create a new task. The light model picks the title. |
| `/task list [--status …] [--limit N]` | Show recent tasks (most-recently-active first). |
| `/task show <id>` | One task with its artifact list and timestamps. |
| `/task fork <id> ["<title>"]` | Copy a task into a new id; lineage recorded. |
| `/task merge <id1> <id2> [...]` | Concatenate two or more tasks into a new one. |
| `/task switch <id>` | Start a Claude session bound to the task (Phase 6 — not yet wired). |
| `/task delete <id> [--remove-folder]` | Drop the registry row. Folder kept unless `--remove-folder`. |
| `/task help` | Print the in-REPL command summary. |

## Walkthrough

A typical first run looks like:

```
> /task new "wire the REPL command surface"
[task] created 0001 "Implement /task commands"
       folder: C:\src\my-project\.task\0001-implement-task-commands

> /task list
ID     STATUS      LAST ACTIVE              TITLE
0001   InProgress  2026-05-07 10:00:00 UTC  Implement /task commands

> /task show 1
[task] 0001 "Implement /task commands"
       home:    C:\src\my-project
       status:  InProgress
       parent:  (none)
       created: 2026-05-07 10:00:00 UTC
       active:  2026-05-07 10:00:00 UTC
       artifacts:
         description.md  2026-05-07 10:00:00 UTC
         index.md        2026-05-07 10:00:00 UTC
         progress.md     2026-05-07 10:00:00 UTC

> /task fork 1
[task] forked 0001 -> 0002 "Implement /task commands (2)"
```

The fork copies every `.md` file from the source folder into the new one
(`.task/0002-…/`) and records `parent_task_id = 1` on the new row, so lineage
is auditable later.

## Commands in detail

### `/task new "<description>"`

Creates a new task. The free-form `<description>` becomes the body of
`description.md` in the new task folder; the **title** is generated by the
light model (Haiku, by default) from that same text — usually 3–6 words.

The first time you call this on a machine, InfiniContext also creates the
SQLite registry at `~/.infinicontext/infinicontext.db` and seeds the schema.

```
> /task new "investigate why the migration takes 6 minutes"
[task] created 0003 "Investigate slow migration"
       folder: C:\src\my-project\.task\0003-investigate-slow-migration
```

The description can be either quoted or bare:

```
> /task new "with quotes"
> /task new without quotes is also fine
> /task new 'single quotes work too'
```

If the title contains characters that don't fit a folder name (spaces,
punctuation, accents), the slug normalises to ASCII kebab-case (`Café au lait`
→ `cafe-au-lait`).

**Requires** `ANTHROPIC_API_KEY` for the title call. If the key is missing,
this command returns `[task] error: …` and the row isn't created. Other
`/task` commands keep working.

### `/task list`

Most-recently-active tasks first. Two optional filters:

- `--limit N` — return at most `N` rows (positive integer).
- `--status <state>` — `inprogress` (alias `active`, `in-progress`) or `idle`.

```
> /task list --status inprogress --limit 5
ID     STATUS      LAST ACTIVE              TITLE
0007   InProgress  2026-05-07 11:42:13 UTC  Stage 2A Phase 6 wire-up
0001   InProgress  2026-05-07 10:00:00 UTC  Implement /task commands
```

Aliases: `/task ls`.

### `/task show <id>`

Both decimal (`42`) and zero-padded (`0042` — the form `/task list` prints) ids
are accepted.

```
> /task show 7
[task] 0007 "Stage 2A Phase 6 wire-up"
       home:    C:\src\my-project
       status:  InProgress
       parent:  0001
       created: 2026-05-07 11:30:01 UTC
       active:  2026-05-07 11:42:13 UTC
       artifacts:
         description.md  2026-05-07 11:30:01 UTC
         index.md        2026-05-07 11:42:13 UTC
         plan.md         2026-05-07 11:42:13 UTC
         progress.md     2026-05-07 11:42:13 UTC
```

Aliases: `/task get`.

### `/task fork <id> ["<title>"]`

Creates a child task that starts as a copy of `<id>`. All `*.md` files are
copied (preserving mtimes) and `parent_task_id` is set on the new row.

Without an override title, InfiniContext appends or increments a `(N)` suffix:

```
> /task fork 7
[task] forked 0007 -> 0008 "Stage 2A Phase 6 wire-up (2)"
> /task fork 8
[task] forked 0008 -> 0009 "Stage 2A Phase 6 wire-up (3)"
```

Pass an explicit title when forking is conceptually a divergence rather than
a continuation:

```
> /task fork 7 "Spike: alternative session-startup design"
[task] forked 0007 -> 0010 "Spike: alternative session-startup design"
```

### `/task merge <id1> <id2> [...]`

Combines two or more tasks into a new task. Currently only the
**deterministic concat** tier is implemented: for every filename present in
any source, the merged folder gets a single file containing each source's
content under a labelled section divider. The merged `index.md` lists the
resulting files.

```
> /task merge 1 7
[task] merged 0001, 0007 -> 0011 "Merge of 0001 + 0007"
       Note: only DeterministicConcat tier is implemented in MVP.
```

The merged row's `parent_task_id` is left `null` because the schema records
only a single parent; multi-parent lineage is post-MVP. The source ids are
preserved in the merged title and in section headings inside each merged
file.

All sources must share the same `home_cwd`. Cross-repo merges aren't
supported in MVP.

### `/task switch <id>`

Starts a Claude session pointed at the task. **Phase 6 — not yet wired.**
Today this prints a placeholder:

```
> /task switch 7
[task] /task switch is implemented in Phase 6 (not yet functional). Task 0007 would have been activated.
```

When Phase 6 ships, `/task switch` will spawn `claude` with the task's
`home_cwd` and prefix the first user message with a pointer to the task
folder and the `infinicontext-task` skill.

### `/task delete <id> [--remove-folder]`

Drops the registry row. By default the on-disk `.task/<id>-<slug>/` folder is
**left in place** — committed task content survives a registry cleanup. Pass
`--remove-folder` (before or after the id) to also delete the folder.

```
> /task delete 7
[task] deleted 0007 "Stage 2A Phase 6 wire-up"
       folder left in place: C:\src\my-project\.task\0007-stage-2a-phase-6-wire-up
       (pass --remove-folder to also delete the on-disk task folder)

> /task delete 7 --remove-folder
[task] deleted 0007 "Stage 2A Phase 6 wire-up"
       removed folder: C:\src\my-project\.task\0007-stage-2a-phase-6-wire-up
```

Refuses to delete a task whose status is `InProgress` (would pull the rug from
under an active session); flip it `Idle` first, or end the session.

If the deleted task has children (forks pointing at it via `parent_task_id`),
the children's parent reference is **cleared** rather than cascade-deleted —
multi-step lineage is informational and the forks themselves remain. The
output reports the orphan count when it's non-zero.

Aliases: `/task rm`.

Useful for the stale-data scenario where a task's `home_cwd` was wiped (e.g.
it pointed at a `bin/Debug` folder that got rebuilt) and you want to drop the
dangling registry row.

### `/task help`

Prints the in-REPL summary. Equivalent: `/task ?`, `/task --help`, or just
`/task`.

## Where things live

```
<your repo>/
└── .task/
    ├── 0001-implement-task-commands/
    │   ├── index.md         ← always present (mandatory artifact)
    │   ├── description.md   ← always present
    │   ├── progress.md      ← always present
    │   └── plan.md          ← optional, agent-created
    └── 0002-…/

~/.infinicontext/
└── infinicontext.db            ← SQLite registry (host-only, never agent-readable)

~/.claude/skills/infinicontext-task/
└── SKILL.md                 ← installed once on first host launch
```

The `.task/` folder is repo-local: tasks travel with the codebase. The
SQLite DB and the skill folder are host-global: they're per-machine.

The agent never reads SQLite directly. All durable task content lives as
plain markdown the agent can edit with `Read` / `Edit` / `Write`.

## Configuration

Two settings keys matter for tasks:

```jsonc
// settings.json (or settings.user.json)
{
  "tasks": {
    "dbPath": null   // null → ~/.infinicontext/infinicontext.db; ":memory:" → ephemeral
  },
  "models": {
    "light": {
      "id": "claude-haiku-4-5"   // model used for /task new title generation
    }
  }
}
```

`tasks.dbPath` accepts an absolute path, `:memory:` (ephemeral, useful for
tests), or `null` (default). It can also be set via the
`INFINICONTEXT__TASKS__DBPATH` environment variable.

## Troubleshooting

**`[task] subsystem is unavailable (see startup warnings).`**
Host startup couldn't open the SQLite DB or construct the light-model client.
Check the log file (`logs/<timestamp>.log`) — the warning has the underlying
exception. Common causes: read-only home directory, permissions on
`~/.infinicontext/`. The host stays usable for everything except `/task`.

**`[task] error: …` on `/task new`**
Most often this is a missing `ANTHROPIC_API_KEY` — the light model can't be
called. Set the env var; other `/task` commands keep working without it.

**`[task] error: Source task N not found.`**
Self-explanatory. `/task list` shows current ids.

**Migration history has a gap / DB ahead of code**
The host refuses to start if the SQLite DB is in a state that doesn't match
the running code (typically because you downgraded). Either upgrade back, or
delete `~/.infinicontext/infinicontext.db` (loses your registered tasks but
preserves the on-disk `.task/` folders, which are the real source of truth
for content).

## Current MVP scope

Things `/task` doesn't do yet (each lands in a later phase):

- `/task switch` — wires up the Claude session. Phase 6.
- Multi-session coordination via MCP locks. Phase 7.
- Light-model and full-model merge tiers. Post-MVP.
- Task rename and archival. Post-MVP. (`/task delete` ships in 2A.)
- Cross-repo tasks (single `home_cwd` only). Post-MVP.
