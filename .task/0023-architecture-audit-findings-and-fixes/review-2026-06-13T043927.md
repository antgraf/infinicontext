### [suggestion] C4 .git/ denylist only inspects the first path segment
- Reviewers: security
- Location: `src/InfiniContext.Core/Review/AutoApplyExecutor.cs`
- Why: The denylist is the defense-in-depth guard against a model planting version-control payloads (core.fsmonitor, hooks). Anchoring on segments[0] leaves nested .git directories writable. Exploitability is limited because the post-apply gate runs build/test in the repo root, so a nested .git only triggers on a later git op in that subtree — hence suggestion.
- Detail: AutoApplyExecutor.DenylistReason refuses writes to .git/ only when segments[0] == '.git'. A nested .git directory (submodule/.git/config, vendor/repo/.git/hooks/pre-commit) is not refused.
- Suggested fix (edit):
  Before:
  ```
          // .git/ internals — hooks/, config (core.fsmonitor → arbitrary command on every git op), etc.
          if (segments.Length > 0 && segments[0].Equals(".git", FileSystemNaming.Comparison))
              return "auto-apply refused: target is under .git/ (version-control internals)";
  ```
  After:
  ```
          // .git/ internals — hooks/, config (core.fsmonitor → arbitrary command on every git op), etc.
          // Match a .git segment at ANY depth so a nested .git/ (submodule/vendored repo) is refused too.
          if (segments.Any(s => s.Equals(".git", FileSystemNaming.Comparison)))
              return "auto-apply refused: target is under a .git/ directory (version-control internals)";
  ```
- Reviewer confidence: 0.45
- Coordinator confidence: 0.75
- Coordinator note: This is the only finding with a concrete kind=edit fix, but reviewer confidence is 0.45 (well below the 0.9 auto_apply gate). The fix also broadens the denylist semantically (any-depth match) which could legitimately block writes to non-VCS paths that happen to contain a '.git' segment, so it warrants human review rather than auto-application. Suggestion severity is correct given limited exploitability. needs_user.
