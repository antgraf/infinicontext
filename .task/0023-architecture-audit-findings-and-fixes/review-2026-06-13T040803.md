- Reviewers: tests
- Location: `tests/InfiniContext.Tests/Mcp/Tasks/LockRegistryTests.cs`

- Fix applied (edit):
  Before:
  ```
      [Fact]
      public void Acquire_validates_inputs()
      {
  ```

  ```
      [Fact]
  ```

### [warning] C4 auto-apply denylist misses nuget.config / global.json (build-time RCE vector)
- Reviewers: security
- Location: `src/InfiniContext.Core/Review/AutoApplyExecutor.cs`
- Why: The auto-apply gate runs dotnet build/test against the modified tree under the host account. A model-emitted nuget.config can repoint package sources to an attacker-controlled feed (arbitrary code on restore); a planted global.json can pin a malicious SDK. Matching is by extension, not filename, so these slip through the one unconditional guard.
- Detail: AutoApplyExecutor.DenylistReason refuses .git/, .github/workflows/, and MSBuild project files, but not nuget.config or global.json, both of which steer the executor's own post-apply 'dotnet build' restore step.
- Suggested fix (edit):
  Before:
  ```
          // Build-system files are executed as MSBuild logic during the gate's `dotnet build`.
          var ext = Path.GetExtension(norm);
  ```
  After:
  ```
          // NuGet/SDK config files steer the gate's `dotnet build` restore: a planted nuget.config
          // can redirect package sources to an attacker-controlled feed (arbitrary code on restore),
          // and global.json can pin a malicious/unexpected SDK. Refuse them by filename.
          var fileName = Path.GetFileName(norm);
          if (fileName.Equals("nuget.config", FileSystemNaming.Comparison)
              || fileName.Equals("global.json", FileSystemNaming.Comparison))
              return $"auto-apply refused: target is a NuGet/SDK config file ({fileName})";
  
          // Build-system files are executed as MSBuild logic during the gate's `dotnet build`.
          var ext = Path.GetExtension(norm);
  ```
- Reviewer confidence: 0.60
- Coordinator confidence: 0.60
- Coordinator note: Legitimate and concrete denylist hardening with a clean edit, but reviewer confidence is 0.6 (below the 0.9 auto_apply gate). The threat is real (build-time RCE on restore) and the fix is plausibly correct, but I cannot confirm the exact casing/comparison semantics of FileSystemNaming.Comparison vs. nuget.config's case-insensitive matching, nor whether legitimate diffs commonly touch these files. Surface for operator sign-off rather than auto-apply.

### [warning] LongLivedCliLightModelService disposes its semaphores while a concurrent call may be parked on them
- Reviewers: code
- Location: `src/InfiniContext.Core/LightModel/LongLivedCliLightModelService.cs:192-197`
- Why: Disposing a SemaphoreSlim does not release parked waiters and throws on a subsequent Release from a holder. With multiple concurrent callers plus host shutdown, an in-flight turn can fault with ObjectDisposedException or strand a waiter.
- Detail: DisposeAsync disposes both _turnLock and _lifecycleLock. A caller past the top-of-ExecuteAsync _disposed check awaiting _turnLock.WaitAsync (or holding it and about to Release) will observe ObjectDisposedException once Dispose runs. M7 deliberately avoided this for ClaudeSession by not disposing _writeLock, yet M25 added _turnLock here and states the single-caller assumption cannot hold.
- Suggested fix: _none_
- Reviewer confidence: 0.50
- Coordinator confidence: 0.70
- Coordinator note: Plausible concurrency hazard consistent with the M7 precedent cited, but the reviewer provided no concrete fix and confidence is 0.5. The correct remedy (drain/quiesce before dispose, or stop disposing the lock as M7 did) is a design call. Needs user.
